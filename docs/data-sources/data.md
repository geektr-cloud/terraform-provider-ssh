# ssh_data (Data Source)

Reads remote files and executes commands or scripts over SSH. Each read establishes a fresh SSH connection and closes it when the operation finishes.

Every operation writes its result to `values`, keyed by the operation's `key`. This data source has no per-operation `sensitive` flag and no `sensitive_values` map: results are persisted in state as ordinary values.

If any result is sensitive, use `data.ssh_sensitive_data` instead. It has the same connection, sudo, timeout, and operation configuration, marks `values` sensitive for display, and suppresses remote stderr in error diagnostics.

- `file` reads a regular file (following a symlink to a regular file) and requires valid UTF-8. Directories and special files are rejected.
- `command` runs a non-empty argv. The provider shell-quotes each argument; shell operators inside an argument are not interpreted.
- `run` feeds the script body to the configured interpreter over stdin (`<shell> -s`), so no script file is written and the script does not appear in the remote process argv.
- Every `file`, `command`, and `run` block accepts `trim`, which defaults to `true`. After UTF-8 validation, `strings.TrimSpace` removes leading and trailing Unicode whitespace from the complete result. Set `trim = false` to preserve exact output, including trailing newlines. A whitespace-only result becomes an empty string. Trimming happens after the raw-output size check.
- All operations validate before any remote action. They run in ascending `index` order. Same-index operations have a deterministic provider order. The first failure aborts the remaining operations and returns no partial map.

The per-item output limit is 512 KiB by default. It can be changed only through the `SSH_PROVIDER_MAX_OUTPUT_SIZE` environment variable (bytes, positive integer). There is no HCL argument and no unlimited mode.

~> Data source schemas cannot be versioned or state-upgraded. Configurations written for the removed `sensitive` block argument and `sensitive_values` map must be migrated explicitly. See [Migration from block-level sensitivity](#migration-from-block-level-sensitivity).

## Example Usage

```hcl
data "ssh_data" "inspect" {
  conn = data.ssh_conn.server.conn

  file {
    key  = "config"
    path = "/etc/myapp/config.yaml"
  }

  command {
    key     = "kernel"
    command = ["uname", "-r"]
  }

  run {
    key    = "services"
    script = "systemctl list-units --type=service --no-legend\n"
    envs   = { LANG = "C" }
  }
}
```

## Migration from block-level sensitivity

The former `file`, `command`, and `run` blocks accepted `sensitive = true`, and this data source exposed a `sensitive_values` map. Both are removed.

- Move operations whose results must be display-redacted to `data.ssh_sensitive_data`. Remove the `sensitive` argument from each block; the whole `values` map is sensitive there.
- Replace every reference to `.sensitive_values["key"]` with `.values["key"]` on the chosen data source.
- Review `trim`. It now defaults to `true`; set `trim = false` on any block that must keep leading or trailing whitespace, including a trailing newline.
- Refresh state after updating the configuration. A data source schema cannot be versioned, so there is no automatic state migration.
