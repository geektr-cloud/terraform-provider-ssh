# ssh_resource (Resource)

Manages a collection of independent remote files and directories over SSH. The resource owns only explicit paths. It never recursively owns or deletes remote content.

- `path` must be a cleaned absolute path and must not be `/`.
- The final target must not be a symbolic link. Symlinks in ordinary parent paths are allowed.
- If an unmanaged target already exists, apply fails unless `auto_import = true`. Adoption takes over the exact path and converges it to configuration; it does not adopt children recursively.
- A managed directory owns only the directory itself. Destroy uses `rmdir`; a non-empty directory fails.
- Create and update upsert paths from shortest to longest so parents precede children. Updates delete removed or type-changed paths first. Writes are not transactional; successful paths are retained in state if a later path fails.
- Files are written through a same-directory temporary file restricted to `0600` before content is written. Mode and ownership are applied before the atomic rename; owner/group names are resolved before the target is touched.
- A newly created directory is removed best-effort if its mode or ownership cannot be applied.
- Ordinary `content` writes and refresh reads share the `SSH_PROVIDER_MAX_OUTPUT_SIZE` cap. A larger value fails apply or refresh instead of being written or read without a bound. Write-only content is not subject to this cap and its digest is streamed.
- Missing paths are removed from state during refresh and recreated on the next plan. Unmanaged paths are ignored.

`file` sets exactly one of `content` or `content_wo`. Empty string is valid content. `content_wo` is a write-only attribute whose plaintext is never written to plan or state; only `content_sha256` is persisted. The digest is a content identity, not encryption, and low-entropy values may be guessed offline.

`mode`, `owner`, `uid`, `group`, and `gid` can be set at the top level as defaults and overridden per path block. `owner` conflicts with `uid`; `group` conflicts with `gid`. When omitted, mode derives from `umask` and ownership follows the effective SSH identity (normally root after sudo escalation).

When an ordinary operation fails with a permission error, the resource retries the same operation with `sudo -n`. Other errors do not trigger escalation. All sudo use is non-interactive.

## Example Usage

```hcl
resource "ssh_resource" "app" {
  conn  = data.ssh_conn.server.conn
  umask = "022"

  directory {
    path = "/opt/myapp"
    mode = "0755"
  }

  file {
    path    = "/opt/myapp/config.yaml"
    content = "listen: 0.0.0.0:8080\n"
    mode    = "0644"
  }

  file {
    path       = "/opt/myapp/secret"
    content_wo = var.stable_secret
    mode       = "0600"
  }
}
```
